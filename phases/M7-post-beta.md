# M7 — Post-beta (P40–P50)

The owner may reorder these after beta feedback (Q-39). Each phase gets a full detailed write-up, in the same format as M0–M6, as its first step: architect (opus) drafts it in `target/plans/`, and the orchestrator moves it into this file before implementation starts.

| Phase | Tier | Size | Depends on | Scope | Decisions |
| --- | --- | --- | --- | --- | --- |
| P40 — Estimates, progress invoicing, sales orders, recurring invoices, retainage | H | L | P20–P22 | Estimates with status and conversion; progress invoicing by percent or line with remaining shown; sales orders (open/partial/closed); recurring invoices via template schedules (Q-256); retainage receivable and release invoice. Acceptance: three progress invoices bring the remaining amount to exactly zero; retainage release clears the receivable. | Q-52, Q-83 |
| P41 — Purchase orders and item receipts | M | M | P17, P24 | POs (open/partial/closed); receive with or without a bill; convert item receipt to bill; "Select PO" on Enter Bill. Acceptance: converting a receipt never double-posts inventory. | — |

| P45 — Accountant tools | M | L | P28, P29 | Batch reclassify, fix unapplied payments/credits, bulk write-offs, forecasts and budgets by project/tag, fixed-asset register (user-entered depreciation), working trial balance export to Vibe Trial Balance, 1099 export to Vibe 1099. | Q-21–Q-23 (bulk entry moved to beta P15A — Bulk Entry, Q-252, Q-256) |

| P48 — Statement of cash flows and calendar | M | M | P28 | Statement of Cash Flows (indirect method, account-to-section mapping with defaults); calendar month view of bills, invoices, and template entries (Q-256). | Q-64, Q-67 |
| P49 — Work copies and bring back changes | H | L | P08, P33, P36 | "Make a work copy" from the main company records a starting point (engine change tracking: every transaction and list record gets a change log entry since that point). On the main company, "Bring back changes" opens a work copy and lists every new, edited, voided or deleted transaction and every new or changed list entry made in it since the starting point; anything also changed in the main company since then is a conflict shown side by side, and the owner picks which version to keep each time (Q-269); nothing is applied until the owner confirms. Changes post through the engine (audit trail, closing-date password flow for closed periods, exact money), matching names and accounts by id first and by name second; a summary and a verified backup before applying (non-negotiable 9). Acceptance: a work copy with 50 new and 5 edited transactions merges exactly once (rerunning finds nothing new); a conflicting edit is never applied without the owner's choice; trial balance equals the expected result. | Q-268, Q-269 |
| P50 — MCP bookkeeper | H | L | P07, P29, P33, all beta forms | An opt-in MCP server lets an AI tool (e.g. Claude Desktop) work in a company like a human bookkeeper: every action a person can take through the app's commands and forms (the P07 tool table is the tool list), posting through the engine as any user would. **Reach:** this computer (stdio/local socket) and LAN workstations through LAN mode's TLS pinning (Q-325); no internet listener. **Identity:** each MCP connection is its own user with a role set by the admin; audit trail shows "via MCP (connection name)" (Q-326). LAN workstations pair with a one-time code exchanged for a token kept in that PC's keychain; the admin can revoke any connection (Q-330). **Admin switches, per company:** MCP on/off; then Read, Create, Edit, Delete/Void and Send & print each on/off, each with its own "Require review" (Q-327, Q-329). First turned on: Read on, all writes off, review on (Q-328). **Never through MCP:** users, roles and MCP settings; closing date and its password, edits in closed periods; backup, restore and company delete (Q-332). **MCP Activity window** (status-bar and Home count): Waiting (each proposed change shown in full; Accept posts it, Open shows it prefilled in its form, Reject), Done (every MCP change with before/after and Undo), Rejected. **Undo** any time (Q-331): created items are voided (deleted if never posted), edits restored to the prior version, deletes/voids restored, all through the engine with the audit trail; blocked with a plain explanation when something else now depends on it (e.g. a payment applied to an MCP invoice), and closed periods need the closing-date password (a human only). Documents: read attachments and attach files through A03 intake; attaching counts as Edit (Q-333). Amounts from MCP are allowed only when the admin turned on writes (non-negotiable 4 amended, Q-324); review makes each change wait for a human accept. Secrets never exposed (non-negotiable 11). Tests: every tool honours each switch (property test across the tool table); review queue posts exactly what was shown; undo restores trial balance and the record exactly; revoked token refused; off-limits tools refused even for an admin-role MCP user; LAN pairing over TLS. Acceptance: an MCP client enters a bill, pays it and reconciles with review on, each step waiting until accepted; undoing all of it returns the trial balance exactly to the start; turning Create off refuses the next create with a plain message. | Q-16, Q-324–Q-333 |
