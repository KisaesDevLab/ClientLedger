## Engine facts (scout, pin 5a9a8700; paths under `engine/packages/api/src/`)

- `GET /api/v1/bills/payable?contactId&dueOnOrBefore` (`routes/bills.routes.ts:60`, `services/bill.service.ts:803-886`): rows `txnNumber, contactName, txnDate, dueDate, discountDate, discountPercent, vendorInvoiceNumber, total, amountPaid, creditsApplied, balanceDue, billStatus, paymentTerms, daysOverdue`, plus `credits[]` (`id, txnNumber, contactId, txnDate, total, balanceDue, memo`). Only posted, received (U-87) bills with a balance.
- `POST /api/v1/bill-payments` (`routes/bill-payments.routes.ts:40`, `services/bill-payment.service.ts:150-529`): `bankAccountId, txnDate, method, bills[{billId, amount}], credits[{creditId, billId, amount}], memo, printedMemo, referenceNumber, printLater`. One payment per vendor. **`bills[].amount` is the bill's coverage including credits** (cash = amount − credits for that bill, :314-325). Response 201 `{payments[]}` with `netPayment`. Closing date: `ap-closing-v1`.
- `GET /bill-payments/:id` (returns `billApplications`, `creditApplications`), `POST /:id/void` (Idempotency-Key, `expectedUpdatedAt`). No edit (`TXN_EDIT_UNSUPPORTED`).
- Print later → `printStatus='queue'`; `GET /checks/print-queue` includes bill payments; `GET /checks/settings` gives the next number.

## Engine PR (WP-E, one branch `clientledger/pay-bills`, opus engine-implementer)

Rows U-101–U-104 in UPSTREAM.md. Capabilities: `bill-discounts-v1`, `idempotency-pay-bills-v1`, `bill-payment-check-number-v1` (U-104 is a fix, no capability).

- **U-101 discounts.**
  - `bills[].discountAmount` (optional, ≥ 0, 2 places) and a top-level `discountAccountId`. Rule per bill: `amount + discountAmount ≤ balanceDue` (amount keeps its meaning: coverage including credits). Credits per bill ≤ amount, as today.
  - `discountAccountId` defaults to the company setting `billDiscountAccountId` (new, on the company/AP settings the engine already has; readable and settable). Discount > 0 with neither set → 400 code `DISCOUNT_ACCOUNT_REQUIRED`.
  - Posting per vendor payment: DR A/P (Σ cash + Σ discount) / CR bank (Σ cash) / CR discount account (Σ discount); the existing credit applications are unchanged. Exact `assertBalanced` (U-65).
  - Applications: write `bill_payment_applications.discount_amount`. A bill covered only by credits + discount (cash 0, discount > 0) must still get its row: change `CHECK (amount > 0)` to `CHECK (amount >= 0 AND amount + discount_amount > 0)`. This is non-additive → add a `WIDENED_CHECKS` entry in `tenant-portability/compat.ts` (the compat test fails otherwise, as on U-94). `recomputeBillStatus` already nets `discount_amount` — verify with a test.
  - A vendor whose net cash is 0 (all credits/discount) still gets a payment record with amount 0? Keep today's behavior for credits-only; with a discount, post the payment (bank line 0 omitted). State in a test.
  - Void reverses the discount lines and restores the bill balance.
  - `/bills/payable?paymentDate=YYYY-MM-DD`: each row adds `discountAvailable` = round(balanceDue × discountPercent / 100, 2) half away from zero when paymentDate ≤ discountDate, else "0.00"; also `updatedAt`. Engine test: 218.44 at 2% → 4.37.
- **U-102** Idempotency-Key on `POST /bill-payments` (`idempotent({successStatus: 201})`, `x-idempotency: true`), add the route to `idempotency_ap_v1_routes.txt` (or its equivalent list).
- **U-103** `checkNumber` (optional, integer string) for `method:'check'` with `printLater:false`: payments get consecutive numbers in vendor order (the order the response lists them), the counter moves to max(counter, last + 1). Duplicate number in the bank account → 409 `CHECK_NUMBER_IN_USE`. Without it, today's behavior.
- **U-104** company scope: `/bills/payable` (bills and credits), `GET /bill-payments`, `GET /bill-payments/:id` filter by `companyId`.
- Regenerate `engine/openapi.json`. Engine tests incl. the mockup penny case: bills 1,286.40 + 1,412.06 + 218.44 (2% → 4.37) + 3,915.00 with CM 250.00 → net 6,577.53; bank 84,210.55 → 77,633.02; partial payment leaves the right balance; discount posts to the discount account; void reverses.

## Decisions (add to QUESTIONS.md Open, P18 rows)

- Q-P18a Discount account: company setting `billDiscountAccountId`; Set Discount dialog has a Discount account picker defaulting to it (QBD-like); if unset and a discount is taken, the dialog asks for one and saves it as the default. 
- Q-P18b Totals row: Amt due totals every listed bill (mockup shows 7,471.90 incl. the unselected 640.00); Discount, Credits and Amt to pay total the selected bills only.
- Q-P18c "Ending balance after" is the engine's balance minus the selected cash total, shown before paying (a preview, not a re-derived balance); after paying, the engine's balance is re-read.
- Q-P18d Method: Check only (Q-10); the mockup's Card / Bank transfer options are not built (deviation in PR).
- Q-P18e Check numbering: "To be printed" (default, Q-246) queues for P19; "Assign check numbers" sends the first number (Q-P13m rule) and the engine numbers one check per vendor (U-103).
- Q-P18f Bill payments can't be edited (engine); OpenRecord opens a read-only view with Void; to change, void and pay again.
- Q-P18g Stale screen: until U-105 (rows' `updatedAt` checked on pay) the engine answers 400 "exceeds balance due"; the screen reloads the list and says the bills changed.
- Q-P18h Bills marked not received (Q-P17i) don't appear (engine filters them).
